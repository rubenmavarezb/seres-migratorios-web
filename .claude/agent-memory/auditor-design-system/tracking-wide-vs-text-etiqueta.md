---
name: tracking-wide-vs-text-etiqueta
description: Tailwind v4 gotcha — tracking-wide on a component class silently overrides text-etiqueta's 0.04em letter-spacing via the shared --tw-tracking custom property; the fix is tracking-(--text-etiqueta--letter-spacing), not a literal value.
metadata:
  type: project
---

Root cause (confirmed while auditing R07/R08 of `docs/qa-visual/fase-2.md`, diff to `src/styles/theme.css` + `Boton.astro`/`CajaNombre.astro`, 07.09.2026): a Tailwind v4 `text-*` size utility that carries a `--<token>--letter-spacing` companion (e.g. `text-etiqueta` → `--text-etiqueta--letter-spacing: 0.04em`, theme.css line 60) only applies that letter-spacing as a **fallback** for the shared `--tw-tracking` custom property. If a component class already carries an explicit `tracking-*` utility (e.g. `.boton`/`.caja-nombre` had `tracking-wide`, 0.025em), that utility pins `--tw-tracking`, and `text-etiqueta`'s own letter-spacing — applied later as a separate class on the same element via an Astro component's `clases` array — resolves through the pinned `--tw-tracking`, not its own token. Net effect: the element renders at 0.025em, never the intended 0.04em, with zero visual indication anything is wrong (no console warning, correct-looking class list).

**How to catch it in a future audit**: grep `theme.css` for any `@layer components` class that combines a `tracking-*` (or `leading-*`) Tailwind utility with a component later receiving a `text-<rol>` size utility from its `.astro` file's `clases` array. If the rol's own `--text-<rol>--letter-spacing` token differs from the component class's `tracking-*`, that's the bug.

**Correct fix** (applied for `.boton`/`.caja-nombre`, R07/R08): replace the literal `tracking-wide` with `tracking-(--text-etiqueta--letter-spacing)` — Tailwind v4's parens shorthand for `letter-spacing: var(--text-etiqueta--letter-spacing)`. This is NOT a new arbitrary value — it references the existing `@theme` token by name, so it stays in sync if the token's value ever changes, and it isn't a "color fuera de token" or similar violation since it resolves to the same custom property `text-etiqueta`'s own fallback chain reads. A literal `tracking-[0.04em]` would produce the same number today but silently drift from the token later — prefer the `(--token)` form whenever fixing this pattern.

See also [[etiqueta-line-height-is-per-component]] for the related line-height question on the same components, and [[text-size-utility-no-pisa-leading-none]] for the confirmed non-bug counterpart: a bare `text-xs`/`text-etiqueta` (no accompanying `leading-*`) does NOT clobber `leading-none` the way `tracking-wide` clobbers letter-spacing, because it only reads `--tw-leading` rather than setting it.

**Confirmed non-bug variant (R11 of `docs/qa-visual/fase-2.md`, `FichaFotografo.astro`'s Instagram handle, 07.09.2026):** `tracking-(--text-etiqueta--letter-spacing)` combined with `text-metadatos` (13px, not `text-etiqueta`/14px) on the same element is correct, not a mismatched-role smell — it exactly mirrors `design/ds/components/fotos/FichaFotografo.jsx`'s inline instagram-link style (`fontSize: var(--tipo-metadatos)`, `letterSpacing: var(--tipo-etiqueta-letter-spacing)`). The reference JSX itself borrows the etiqueta role's letter-spacing for a metadatos-sized element; don't flag this combination as a token mismatch when it traces back to that JSX.
